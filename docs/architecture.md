# 设计笔记

> 这份文档记录「为什么这么做」，以及对应的实测数据。改动这些地方之前建议先读一遍。

## 总体

- **零第三方依赖**：只用 BCL + WPF。没有 DI 容器、没有 MVVM 框架、没有 JSON 库之外的东西。
- **进程常驻、窗口按需创建**：启动只加载数据并创建日历窗口，编辑窗 / 待定区 / 便签在第一次用到时才创建。
- **软件渲染是刻意的**（`RenderMode.SoftwareOnly`）：这些窗口全是半透明图层窗口，
  在远程桌面、虚拟机和多显卡机器上硬件合成反而更容易闪；实测软件渲染下打字 72–93 fps，够用。
- **GC 精简堆**：`System.GC.ConserveMemory=5`、关闭并发 GC，空闲时把内存还给系统。

## 窗口层级

- 日历是普通顶层窗口（`ShowInTaskbar=False`，不进 `Alt+Tab`）。
- 编辑窗与待定区通过 `Window.Owner` 成为日历的**从属窗口**：Windows 保证从属窗口始终画在主人之上，
  所以点日历不会把卡片压到下面。
- 悬浮预览是 click-through 的 `WS_EX_NOACTIVATE | WS_EX_TRANSPARENT` 工具窗口，层级固定在日历之上、卡片之下。
- 卡片位置由 `CalendarHost` 统一计算：开在日历外侧（右优先，放不下放左边），
  日历移动时把卡片按相对偏移一起搬走，而不是每帧重算。

## 玻璃卡片

`Theme/Theme.xaml` 里的 `GlassBrush` 是几乎不透明的白色渐变（`#F7FEFFFF → #F6F9FE → #FAFCFF`），
配合 1px 白色描边和 14–18px 圆角，得到「半透明白玻璃」的观感。

投影**没有用** `DropShadowEffect`，而是由 5 层极淡的圆角描边叠出来（纯色，无模糊）：

| 方案 | 第一次弹出窗口 | 便签放大到 900×820 打字 |
| --- | --- | --- |
| `DropShadowEffect` | 353 ms | 37 fps |
| 5 层调色描边 | 81 ms | 72 fps |

模糊投影每帧都要重算，而描边是纯色几何，视觉上几乎看不出差别。

## 数据

- `Data\schedule.dat`：自定义紧凑二进制，magic `MRD3`，格式版本 3。
  全量常驻内存（每天一个 `DayData`），按天读取 O(1)；待定区作为没有日期的 `DayData` 存在同一文件里。
- 写入：400 ms 防抖 + 原子替换（先写临时文件再 `File.Replace`），另有 `.bak` 备份。
- 旧版 v2 数据可直接读取并升级。
- **实测**：工作集约 100 MB、私有内存约 55 MB、空闲 CPU 0 %、启动 0.3–0.5 s（15 天数据加载 0.5 ms）。

## 剪贴板

WPF 的 `Clipboard` 默认走 OLE：`OleSetClipboard` + `OleFlushClipboard`，被占用时重试 10 次 × 100 ms，
最后抛 `COMException 0x800401D0 (CLIPBRD_E_CANT_OPEN)`。

而 `TextBoxBase.Cut()` 是「先复制、再删除」，失败点正好卡在两者之间——
于是出现「文字进了剪贴板、却还留在便签里」的半成功状态，界面还会卡住 1 秒。
这就是历史上「`Ctrl+X` 有时候不灵」的真正原因。

现在用 `Core/ClipText.cs` 直接调 Win32：`OpenClipboard` / `EmptyClipboard` / `SetClipboardData`（`GMEM_MOVEABLE`），
失败时 50 ms 内返回。编辑器侧的 `Core/ClipboardEdit.cs` 只在**真的写入成功之后**才删除选区，
失败则保留文字并提示，1 秒内重试最多 3 次，且只针对**同一次剪切的确切范围**。

粘贴同样绕开了框架的默认行为：WPF 的 `TextBox.SelectedText = value` 会把光标留在插入内容的**开头**
（实测 `caret=0`，且插入内容处于选中态），接着打字就会跑到粘贴内容前面去。
`ReplaceSelection` 插入后显式把光标移到末尾并滚动到对应行（实测 `caret=5`）。

## 拖拽

- 拖拽只在**每一帧渲染时**处理一次（`CompositionTarget.Rendering`），鼠标消息再密也不会重复计算。
- 拖拽开始时一次性缓存所有行 / 类别的矩形，之后纯数学判位，不再做实时命中测试。
- 浮卡移动不反复调整窗口 Z 序；日历整体拖动同样按帧驱动。
- 拖出卡片时把卡片透明度降到约 14 %，让被它挡住的窗口成为拖动目标（`WS_EX_TRANSPARENT` 在拖动期间切换）。

## 悬浮预览

- 改成「日期 + 类别 + 一行日程」之后，每张卡的元素少了一半（不再渲染备注块）：
  一次「收起再弹出」的整链耗时 9.1 ms → 7.3 ms，切换日期稳态约 2 ms，日历整月重绘 0.6–0.7 ms。
- 列表超出卡片高度时显示一排 `···` 而不是滚动条——浮窗是点击穿透的，滚动条本来也拖不动。
- 启动约 1.2 秒后在空闲时**离屏预热**一张日程卡和一张便签（用完即弃），
  第一次点日期 / 双击任务栏的等待从约 350 ms 降到 80–110 ms。

## 任务栏双击

任务栏（`Shell_TrayWnd`）是一个整窗口，图标是它的子元素。判断「双击的是空白处」靠 UI Automation：
把鼠标位置转成屏幕坐标，查该点上的自动化元素，落在按钮 / 图标 / 托盘上就不弹便签。
另外还要排除「双击已经最小化的本程序任务栏按钮」，否则会出现「点一下任务栏却新建便签」的错觉。

## 开发自检开关

全部通过命令行参数触发，只有在直接运行 exe 时生效：

| 开关 | 作用 |
| --- | --- |
| `--diag` | 每 10 秒往日志写内存 / 窗口 / GC 统计 |
| `--shot <目录>` | 把各窗口离屏渲染成 PNG（1×，便于比对界面） |
| `--gallery <目录>` | 用内置假数据重新生成 README 截图（2×，桌面背景） |
| `--probe` | 模拟打开编辑窗 / 拖动日历 / 打开待定区，把窗口矩形与 Z 序写入日志 |
| `--typing` | 量便签每次按键 / 每帧耗时（`--typing --hw` 用硬件渲染对照） |
| `--flyout <目录>` | 打开一个真实 `⋯` 浮窗并截屏，核对文字渲染 |
| `--taskbar` | 打印任务栏窗口树，并用 16 个采样点验证「空白 vs 图标」判定 |
| `--frames` | 量打开 / 切换 / 收起编辑窗与待定区的耗时，并自检收起与互斥行为 |
| `--drag` | 用合成鼠标真拖日历挂件和便签，逐帧对比指针位移与窗口位移 |
| `--stack` | 验证层级契约：点日历后它上浮、卡片仍在它之上 |
| `--drop` | 用合成鼠标把日程从编辑窗拖到日历某天，验证落点写进数据 |
| `--ui` | 用合成鼠标 / 键盘逐项自检交互（悬浮卡、类别选中、`Ctrl+Enter`、统计文字等） |
| `--clip` | 反复 `Ctrl+X` 记录编辑器 / 模型 / 剪贴板三方状态，验证不会半成功 |
| `--cliphold <毫秒>` | 用真实窗口占用剪贴板，制造「剪贴板被占用」的场景 |

`--ui` `--clip` `--drop` 之类需要真实输入的工具会先 `WindowEffects.ForceForeground`，
否则合成输入会打到别的窗口上。

运行中若 UI 线程被卡住超过 400 ms，日志会写一行 `ui stall …`（5 秒最多一条），可直接用来定位卡顿。

## 调试技巧

- 日志统一在 `Data\meiri.log`，用 UTF-8 读：`Get-Content Data\meiri.log -Encoding utf8`。
- 修改窗口外观时先跑 `--shot`，不占用屏幕也能看到结果。
- 改交互后先跑 `--ui`，它会自己指出哪一条不成立。
